# PCLA 十日框架计划

> 目标不是十天内做出完整启动器，而是**十天内做出一个能装上、能说出结论、能被别人验证的东西**。

---

## 0. 必先做的取舍

完整启动器要解决三件事：**启动内核**（JVM 起停、LWJGL 替换、GL4ES、输入映射）、
**业务层**（版本、下载、Mod、崩溃分析）、**决策层**（这台机器该怎么配）。

第一件已经被 PojavLauncher / FCL 解决了两遍，重写要几个月；
第三件是空白，而且**我们手上有全网唯一的真机实测数据**。

所以十日计划只做第三件：

| 轨道 | 内容 | 周期 |
|---|---|---|
| **Track A（这十天）** | 设备体检 + 参数决策 + 写入现有实例。不启动游戏。 | 10 天 |
| Track B（后续） | fork Pojav 内核，自研启动 | 3–6 个月 |

Track A 不做启动，就绕开了所有需要几个月才能验证的东西，
而且它**独立可用**——就算 Track B 永远不做完，Track A 也是个有用的工具。

## 3. 已知技术风险（按严重度）

### R1｜Android 11+ 无法直接读写 `Android/data/com.tungsten.fcl`
这是 Track A 的**最大障碍**。FCL 的实例在私有目录下，
普通 App 没有权限，`MANAGE_EXTERNAL_STORAGE` 上架应用商店会被拒。

**对策**：用 SAF（`ACTION_OPEN_DOCUMENT_TREE`）让用户手动选一次 `.minecraft` 目录，
拿持久化 URI 权限。用户体验略差，但合规、且不需要任何敏感权限。
**D3 开始就必须按 SAF 设计，不要等写完再改。**

### R2｜没有电脑，改代码全靠手机
Termux 里能跑 `kotlinc` 自检，但打不出 APK（没有 Android SDK 的磁盘空间和内存）。

**对策**：APK 一律走云构建。`ci/build.sh` 是给 Termux 用的退路（只跑自检）。

### R3｜Gitee 不支持 GitHub Actions
仓库在 Gitee，`.github/workflows/` 不会自动运行。

**对策**：三种选择——(a) 仓库镜像到 GitHub 用 Actions；
(b) 用 Gitee Go（流水线配置格式不同，需单独写）；
(c) 手动跑 `ci/build.sh`。
建议 (a)，因为 GitHub 的 Android 环境最成熟。

### R4｜Compose 代码未经编译验证
当前编写环境没有 Android SDK，UI 层是「按 API 写对」而不是「编译通过」。

**对策**：D1 第一件事就是让 CI 编译一次，把错误一次性收干净。
在那之前不要往 UI 层堆功能。

## 4. 不做什么（明确的负向清单）

- ❌ 不重写启动内核（Pojav/FCL 已经做过两遍）
- ❌ 不做「一键下载整合包」——下载层要处理镜像、分段、断点续传、依赖树，是另一个 10 天
- ❌ 不承诺服务器（爱发电只写「支持开发」）
- ❌ 不在没有实测数据的机型上编参数（宁可用 generic 保守默认）

## 决策记录：默认堆为什么是 2048 而不是 3072

早期版本按「版本系数 × 甜点堆 + 每级渲染距离 128MB」推导，8GB 机器上会算出 3686MB。
两个问题：

1. 渲染距离吃的是显存和 CPU，不是堆。实测 1.18 在 RD17 下用 2048MB 也没 OOM。
2. 堆开太大不会「变快」，只会让 Android 在你玩游戏时把进程杀掉。

现在：默认堆 = 机型实测基线（2048），只有 mod 数量按 4MB/个微调；
运行时证据（young GC 回收率 < 10%）出现后，才由 `DegradeLadder` 一次抬一档到 3072。
安全上限 = min(物理内存 45%, 实测基线 + 1024, 4096)。
